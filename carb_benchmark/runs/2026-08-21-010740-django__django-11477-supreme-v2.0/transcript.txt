I have fixed the issue where [translate_url()](file:///E:/RofU/Supreme/carb_workspaces/django__django-11477/django/urls/base.py#L160-L181) created incorrect or untranslated URLs when URL patterns contained optional groups (named or positional) that were missing in the matched URL.

### Cause of the Issue
When resolving a URL path matching a regex pattern with optional groups, `resolve()` returns a `ResolverMatch` object containing `args` (positional groups) and `kwargs` (named groups). Unmatched optional groups produce `None` values in `match.args` or `match.kwargs`.

When `translate_url()` subsequently called `reverse(to_be_reversed, args=match.args, kwargs=match.kwargs)`, passing `None` values caused `reverse()` to either:
1. Raise `NoReverseMatch` (falling back to returning the untranslated URL), or
2. Match a pattern variant expecting the optional parameter, formatting `str(None)` as `'None'` into the URL string (creating corrupted URLs like `/nl/item/None/42/`).

### Solution
In [django/urls/base.py](file:///E:/RofU/Supreme/carb_workspaces/django__django-11477/django/urls/base.py#L173-L177), `None` values are now filtered out from both `match.args` and `match.kwargs` prior to calling `reverse()`.
