### Summary of Changes

#### Issue
During transition to Django 3.1, setting `DEFAULT_HASHING_ALGORITHM = 'sha1'` was insufficient for multi-instance zero-downtime deployments because Django 3.1's `SessionBase.encode()` used the new `signing.dumps()` format (`base64d:timestamp:signature`), which Django 3.0 instances could not decode.

#### Root Cause
In commit `d4fff711d4c97356bd6ba1273d2a5e349326eb5f` (#31274), the session encoding format was switched to `signing.dumps(...)`. While `SessionBase.decode()` was updated to fall back to `_legacy_decode()` for sessions formatted by older versions, `SessionBase.encode()` always produced the new format regardless of `DEFAULT_HASHING_ALGORITHM`. As a result, older instances (Django 3.0) could not decode sessions generated by Django 3.1 instances even when `DEFAULT_HASHING_ALGORITHM = 'sha1'` was specified.

#### Solution
1. **[base.py](file:///E:/RofU/Supreme/carb_workspaces/django__django-13279/django/contrib/sessions/backends/base.py#L109-L127)**: Added a check in `SessionBase.encode()` to use legacy session encoding (`_legacy_encode()`) when `settings.DEFAULT_HASHING_ALGORITHM == 'sha1'`.
2. **[tests.py](file:///E:/RofU/Supreme/carb_workspaces/django__django-13279/tests/sessions_tests/tests.py#L327-L340)**: Added `test_encode_legacy_hashing_algorithm` in `SessionTestsMixin` to verify that `DEFAULT_HASHING_ALGORITHM = 'sha1'` encodes session data using the legacy format compatible with Django 3.0.
