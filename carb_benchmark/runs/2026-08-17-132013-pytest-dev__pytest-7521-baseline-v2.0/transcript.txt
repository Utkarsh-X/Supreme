I have fixed the issue where `capfd.readouterr()` converted carriage returns (`\r`) to newlines (`\n`).

### Root Cause
In `_pytest/capture.py`, `FDCaptureBinary` creates an instance of `EncodedFile` (a subclass of `io.TextIOWrapper`) around the temporary file capturing file descriptors 1 and 2. Because `newline=""` was omitted when instantiating `EncodedFile`, `io.TextIOWrapper` defaulted to `newline=None`. Under `newline=None`, universal newlines mode translates `\r` and `\r\n` to `\n` on read. In contrast, `CaptureIO` (used for `capsys`) passed `newline=""` so that carriage returns remained untranslated.

### Solution
1. Added `newline=""` when instantiating `EncodedFile` in [`src/_pytest/capture.py`](file:///E:/RofU/Supreme/carb_workspaces/pytest-dev__pytest-7521/src/_pytest/capture.py#L386-L393) so line endings are preserved untranslated during read operations.
2. Added `test_capturing_carriage_return` in [`testing/test_capture.py`](file:///E:/RofU/Supreme/carb_workspaces/pytest-dev__pytest-7521/testing/test_capture.py#L1037-L1043) to test that `\r` is preserved across all capture classes (sys, fd, tee).
3. Added changelog entry in [`changelog/7521.bugfix.rst`](file:///E:/RofU/Supreme/carb_workspaces/pytest-dev__pytest-7521/changelog/7521.bugfix.rst).
### Summary of Changes

As a result, Python's `io.TextIOWrapper` defaulted to `newline=None`, which converts `\r` and `\r\n` line endings into `\n` when reading captured text output.
